# Космо-портфель: расчётный инструмент Кейса 02

Интерфейс по утверждённому макету (`docs/mockup/`) плюс расчётный слой на
стандартной библиотеке Python. Без зависимостей, без ключей, офлайн.

## Запуск

```
python app/server.py            # http://127.0.0.1:8765
```

Без сервера: `python app/build.py` собирает `app/static/data/dashboard.json`,
после чего папку `app/static` можно открыть любым статическим сервером
(`python -m http.server -d app/static`). В этом режиме выбор комбинации
работает внутри уже собранного файла, а экспорт недоступен.

Проверки расчётного слоя:

```
python -m unittest discover -s app/tests -v
```

## Как это устроено

```
app/
├── server.py            сервер: статика + GET /api/dashboard + POST /api/export
├── build.py             собрать dashboard.json; --export пишет results/
├── config/
│   ├── portfolio.json   выбранный портфель (решение гейта)          ← роль E/A
│   ├── model.json       веса, thin_margin_pct, allowed_modes, число предложений ← роль B
│   ├── lots_ui.csv      карточки сервисов: название для интерфейса, описание,
│   │                    пользователь, доступ, KPI, что показать при сбое     ← карточки сервисов (записка)
│   ├── team.json        карточка решения: команда, метод, тезис, шесть управленческих полей ← роли C, D, E
│   └── lots_ru.json     регионы, архетипы и названия лотов без карточки (только подписи)
├── backend/
│   ├── evaluate.py      формулы case_core.py на stdlib + check_details (факт/знак/порог)
│   ├── model.py         перебор, балл, предложения, действия в стрессе   ← роли B, C
│   └── payload.py       сборка dashboard.json, экспорт results/
├── static/              интерфейс: index.html, styles.css, app.js, data/dashboard.json
├── tests/               unittest: формулы, границы, перебор, форма контракта
└── CONTRACT.md          схема dashboard.json
```

Поток данных: `cases/case02/{data,config}` → `backend.evaluate` →
`backend.model` (перебор 5 670 комбинаций, балл, предложения) →
`backend.payload` → `dashboard.json` → `app.js`. Интерфейс не считает
модель: только показывает и выводит производные (см. CONTRACT.md).

## Что делает интерфейс

- **Портфель.** Предложенные комбинации (клик по строке выбирает; сервер
  пересобирает предложения относительно новой выбранной), плитки, девять
  проверок для сценария из шапки (BASE/STRESS), таблица лотов с итогом,
  карточки сервисов (что получает пользователь каждого лота).
- **Сравнение.** Графики ценности/поступлений и c0 относительно лимитов,
  таблица комбинаций с баллом.
- **Стресс.** Матрица запасов по каждому ограничению, действия для
  комбинации, не проходящей STRESS, карточка «Замена».
- Кнопка «Экспорт results/» пишет `results/base.json`, `stress.json`,
  `alternatives.csv` для текущей выбранной комбинации (T5, цифры записки), а
  рядом — `portfolio_detail.csv`, `portfolio_metrics.json`,
  `team_decision_config.json`: те же имена и поля, что у последней ячейки
  стартового notebook организаторов (`cases/case02/Космос_как_инфраструктура.ipynb`,
  README организаторов §8.8), чтобы эксперт сравнил выгрузки один в один.
- Кнопки «?» в каждом блоке — пояснения для эксперта.

## Интеграция: что кому менять

**Роль A (инструмент, канон).** Расчёт сейчас на `backend/evaluate.py` —
повтор формул организаторов без pandas. Для сдачи заменить его на
канонический `case_core.py`:

1. `evaluate.core_backend()` уже оборачивает `case_core.load_case`,
   `evaluate_portfolio`, `check_constraints` (нужен pandas).
2. В `payload._enumerated()` передать эти функции в `model.enumerate_all`
   (`evaluate=..., check=...`); `check_details` оставить для факта/порога
   в интерфейсе или расширить `check_constraints` теми же полями.
3. Прогнать `python -m unittest discover -s app/tests` — цифры должны
   совпасть один в один (тесты фиксируют выбранный портфель, контрольный
   пример из исполненного notebook организаторов FIRE:A, AGRI:C, TRANS:C,
   ENV:A, границы 1300/1180 включительно, итоги перебора 5 670 / 1 031 / 143).
4. Перебор 5 670 комбинаций через pandas займёт заметно дольше секунды:
   кэшировать результат (`functools.lru_cache` уже стоит) или считать
   один раз в `build.py`.

**Роль B (модель выбора).** `config/model.json` — веса и обоснования;
`model.make_scorer` — критерии и нормализация (сейчас min–max по
допустимым в STRESS, критерий «запас по STRESS» = 1180 − c0);
`model.suggest` — правило отбора предложений (лучший режим каждого
допустимого набора лотов + режим A на всех лотах выбранного набора,
топ-N по баллу, плюс отвергнутая с максимумом ценности). Sensitivity ±20 %
по весам: перезапустить `build_dashboard` с изменёнными весами и сравнить
`rank` выбранной комбинации — удобно вынести в отдельный скрипт.

**Роль C (стресс).** `model.stress_actions` формирует список «что можно
сделать» для комбинации `stress.failing`; правило кейса (стоимость лотов
не снижается) соблюдено: только смена режима или состава. Подписи
действий — из `describe_change`.

**Роль E (гейт).** Выбранный портфель — `config/portfolio.json`, id в
формате `FIRE:A|AGRI:B|TRANS:B|ENV:A`. Меняется без правки кода (T2).

**Карточки сервисов (записка).** `config/lots_ui.csv` — файл в формате
«участник 5», который готовит автор карточек сервисов: `lot_id`, «Название для интерфейса», «Короткое
описание», «Основной пользователь», «Режим», «Базовый доступ»,
«Дополнительный доступ», «Главный KPI», «Что показать при сбое». Название
лота в интерфейсе берётся отсюда, поэтому в записке и на экране оно одно;
остальные поля идут в блок «Сервисы портфеля». Строки можно добавлять для
любых лотов; лот без строки показывается по `lots_ru.json` с пометкой
«карточка не подготовлена». Плательщик, оператор, приёмка и риски из полных
карточек в инструмент не выносятся.

**Карточка решения (роли C, D, E).** `config/team.json` — название команды,
метод (`Weighted MCDA`), тезис стратегии и шесть управленческих полей из
notebook организаторов (`payer_opex`, `operator_model`, `supplier_switch_rule`,
`replicable_core`, `local_adaptation`, `stress_decision`; кто какое заполняет —
в комментарии файла). Портфель и веса подставляются из `portfolio.json` и
`model.json`. Экспорт собирает из этого `results/team_decision_config.json`;
на расчёт файл не влияет. Тексты те же, что в записке, по одному-два
предложения.

**Пользовательский режим D.** Не реализован: `access_modes.csv` читается
как есть. Если нужен, добавить строку режима в отдельный файл команды и
подмешивать её в `load_case` с пометкой «допущение команды»; интерфейс
подхватит новую букву автоматически.
