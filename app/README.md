# Космо-портфель: расчётный инструмент Кейса 02

Интерфейс по утверждённому макету (`docs/mockup/`) поверх расчётного движка
команды `src/kosmo`. Без зависимостей, без ключей, офлайн. Свои формулы в
`app/` не хранятся: каждая цифра на экране получена вызовом движка.

## Запуск

```
python app/server.py            # http://127.0.0.1:8765
```

Без сервера: `python app/build.py` собирает `app/static/data/dashboard.json`,
после чего папку `app/static` можно открыть любым статическим сервером
(`python -m http.server -d app/static`). В этом режиме выбор комбинации
работает внутри уже собранного файла, а экспорт недоступен.

Проверки интерфейсного слоя (сверка с движком и с `results/`):

```
python -m unittest discover -s app/tests -v
```

Они же попадают в общий прогон `python -m pytest -q` из корня репозитория.

## Как это устроено

```
app/
├── server.py            сервер: статика + GET /api/dashboard + POST /api/data
├── build.py             собрать dashboard.json; --export пишет results/ движком
├── config/
│   ├── model.json       параметры интерфейса: feasible_scenario, thin_margin_pct,
│   │                    allowed_modes, число предложений
│   ├── lots_ui.csv      карточки сервисов: название для интерфейса, описание, проблема,
│   │                    пользователь, доступ, KPI, эффект, плательщик, риск, при сбое,
│   │                    тиражируемое ядро и местная адаптация          ← карточки сервисов (записка)
│   ├── why_final.json   тексты экрана «Почему FINAL» (формулировки записки)           ← участник 3
│   └── lots_ru.json     регионы, архетипы и названия лотов без карточки (только подписи)
config/team.json         карточка решения: команда, метод, тезис, шесть управленческих полей ← роли C, D, E
├── backend/
│   ├── evaluate.py      обёртка над kosmo: load_case, calculate_all_scenarios, строки проверок
│   ├── model.py         перебор через движок, балл (kosmo.score_variants), предложения, действия в стрессе
│   ├── payload.py       сборка dashboard.json, экспорт results/ через kosmo.export_bundle
│   └── ingest.py        загрузка набора данных в формате организаторов (вкладка «Данные»)
├── static/              интерфейс: index.html, styles.css, app.js, data.js, data/dashboard.json
├── tests/               unittest: сверка с движком и results/, форма контракта, экспорт
└── CONTRACT.md          схема dashboard.json
```

Поток данных: `data/`, `config/case_config.json` (копия файлов организаторов,
сверенная движком по `config/case_checksums.json`) → `kosmo.load_case` →
`kosmo.calculate_all_scenarios` для каждой из 5 670 комбинаций →
`kosmo.score_variants` с весами из `config/weights.json` → `backend.payload`
→ `dashboard.json` → `app.js`. Интерфейс не считает модель: только
показывает и выводит производные (см. CONTRACT.md).

Единые источники, общие с CLI движка (`python -m kosmo ...`):

| Что | Где | Кто меняет |
|---|---|---|
| выбранный портфель | `config/portfolio.json` | решение гейта |
| альтернативы для `alternatives.csv` | `config/alternatives.json` | экономист |
| веса и критерии балла | `config/weights.json` | модель выбора |
| пользовательский режим D | `config/custom_mode.json` (если есть) | движок подмешивает его сам |
| карточка решения для `team_decision_config.json` | `config/team.json` | C, D, E |
| цифры для записки | `results/` | только выгрузка движком |

`app/config/model.json` держит лишь параметры экрана. Балл в интерфейсе
считается той же функцией `kosmo.score_variants`, что и `results/scores.csv`,
но нормализуется по всем допустимым в STRESS комбинациям перебора
(`feasible_scenario`), поэтому значения балла на экране и в `scores.csv`
(нормализация по семи альтернативам) не совпадают и не должны.

## Что делает интерфейс

- **Шапка.** Сценарий (BASE/STRESS) выбирается из выпадающего списка; цифры
  лимитов в самом переключателе не показываются (по решению команды) — они
  во всплывающей подсказке, в пилюле статуса, в плитке c0 и на вкладке
  «Ограничения». Рядом переключатель светлой и тёмной темы (выбор
  запоминается в браузере; без выбора берётся тема системы). Внутри каждой
  страницы — вкладки, адрес вида `#страница/вкладка` (`#portfolio/builder`).
- **Портфель.** «Обзор» — карточки лотов показанного портфеля с режимом и c0,
  место по баллу, плитки показателей, сводка девяти ограничений и проверки
  команды S2; подпись FINAL или «произвольный портфель» с кнопкой
  «Вернуть FINAL». «Конструктор» — эксперт собирает любой портфель: четыре
  разных лота и режим каждого, проверка на повтор лота с понятным текстом,
  «Рассчитать» пересчитывает все экраны движком через сервер; ниже результат
  BASE и STRESS с текстом каждого нарушения («c0 = 1 237.0 > 1 180,
  превышение 57.0 млн руб.»). «Ограничения» — таблица всех девяти проверок
  (условие, требование, факт, запас, статус) плюс строка проверки команды
  S2, помеченная как не канон кейса; рядом блок «BASE и STRESS рядом»
  (лимит, c0, запас, допустимость). «Комбинации» — предложенные комбинации
  с отличиями от показанного портфеля (клик по строке выбирает; сервер
  пересобирает предложения относительно новой выбранной; портфель из
  `config/portfolio.json` остаётся в списке всегда). Ранжируются все
  комбинации, допустимые в STRESS (143); модель выбора — советник, выбор
  портфеля управленческий. Столбец «S2 ≥ 0,60» — диагностическая проверка
  команды из `config/weights.json` → `gates` (якорные платежи / OPEX при
  нулевой коммерческой выручке), на балл и ранг она не влияет.
  Переключатель «S2 как фильтр» в заголовке таблицы (`?gates=filter`)
  показывает, как изменился бы список, если бы S2 была правилом отбора:
  остаются 18 комбинаций, портфель команды первый, а лидер без S2 уходит в
  серую строку «не проходит S2». «Лоты и сервисы» — таблица лотов с итогом
  и карточки сервисов: проблема, пользователь, доступ, KPI, общественный
  эффект, предполагаемый плательщик (всегда с пометкой предположения),
  ключевой риск, что показать при сбое. Карточка свёрнута до лота, режима,
  региона и пользователя; кнопка «Подробнее» раскрывает её отдельно от
  соседних. Ниже блок «Тиражирование: ядро и адаптация» — по
  каждому лоту, что переносится в следующий регион без изменений и что
  настраивается на месте (П8).
- **Почему FINAL.** «Решение» — формулировка команды из
  `app/config/why_final.json` («выбранный после управленческого отбора», не
  математический лидер), таблица именованных альтернатив записки из
  `config/alternatives.json` с баллом и местом (варианты выше FINAL не
  скрыты), блок «что выигрываем и что теряем» против выбранной альтернативы
  (по умолчанию V2), устойчивость выбора. «Разложение балла» — по каждому
  критерию значение, нормированное z, вес и вклад для FINAL и альтернативы
  (те же z, что в `results/ranking_full.csv`). «Сценарий S2» — сценарий
  команды «commercial cash = 0», явно помечен как не официальный STRESS.
- **Сравнение.** «Графики» — ценность/поступления и c0 относительно лимитов;
  «Таблица» — комбинации с баллом и столбцом S2.
- **Стресс.** «Запасы» — матрица запасов по каждому ограничению и S2;
  «Действия» — что можно сделать для комбинации, не проходящей STRESS, и
  карточка «Замена».
- **Данные.** «Текущий набор» (хэши, версия), «Загрузка» (три файла
  организаторов, проверка, предпросмотр, применение), «Формат».
- Интерфейс `results/` не пишет: кнопки экспорта в шапке нет, и серверного
  маршрута записи тоже нет. Выгрузку делают только из командной строки —
  `python -m kosmo export` или `python app/build.py --export`. Обе вызывают
  `kosmo.export_bundle`: для портфеля команды пишут в `results/` (`base.json`,
  `stress.json`, `alternatives.csv`, `scores.csv`, `sensitivity.csv`,
  `repairs_base.csv`, `repairs_stress.csv`, а также `portfolio_detail.csv`,
  `portfolio_metrics.json`, `team_decision_config.json` с теми же именами и
  полями, что у последней ячейки стартового notebook организаторов, README
  организаторов §8.8); для любой другой комбинации — в
  `results/variants/<id>/`, чтобы цифры записки не затирались.
- Пояснения не лежат на экране серым текстом: у каждого блока кнопка «?»,
  по клику открывается подсказка для эксперта (пороги, формулы, правила
  кейса, единицы измерения).
- Сценарий показа на 60–90 секунд — `docs/live-demo.md`; протокол чистого
  запуска — `docs/clean-run.md`.

## Что где менять

**Движок (`src/kosmo`).** Формулы, проверки, заметки, перебор, выгрузка.
Интерфейс их не дублирует; тесты `app/tests` падают, если dashboard
разошёлся с `results/base.json` или с прямым вызовом движка.

**Модель выбора.** `config/weights.json` — критерии, направления, веса,
обоснования (ключ `margin:STRESS:c0_limit` показывается как «запас по
STRESS»). `model.suggest` — правило отбора предложений (лучший режим
каждого допустимого набора лотов + режим A на всех лотах выбранного
набора, топ-N по баллу, плюс отвергнутая с максимумом ценности).
Чувствительность к весам ±20 % уже есть в `results/sensitivity.csv`.

**Стресс.** `model.stress_actions` формирует список «что можно сделать»
для комбинации `stress.failing`; правило кейса (стоимость лотов не
снижается) соблюдено: только смена режима или состава. Подписи действий —
из `describe_change`. Полный список одношаговых замен для портфеля команды —
`results/repairs_stress.csv`.

**Гейт.** Выбранный портфель — `config/portfolio.json` в формате движка
(`name`, `selection` из пар `lot_id`/`mode_id`, `note`). Порядок лотов
не важен: интерфейс приводит id к порядку `lots.csv`.

**Карточки сервисов (записка).** `app/config/lots_ui.csv` — файл в формате
«участник 5», который готовит автор карточек сервисов: `lot_id`, «Название для интерфейса», «Короткое
описание», «Основной пользователь», «Режим», «Базовый доступ»,
«Дополнительный доступ», «Главный KPI», «Что показать при сбое», «Проблема»,
«Предполагаемый плательщик» (всегда с пометкой предположения), «Ключевой
риск», «Повторно используемая часть», «Местная адаптация», «Общественный
эффект». Название лота в
интерфейсе берётся отсюда, поэтому в записке и на экране оно одно; остальные
поля идут в блок «Сервисы портфеля», а два последних столбца — в блок
«Тиражирование: ядро и адаптация» той же вкладки (П8; те же формулировки, что
в `docs/team/participant-2/service_cards_full.csv`). Строки можно
добавлять для любых лотов; лот без строки показывается по `lots_ru.json` с
пометкой «карточка не подготовлена». Оператор, приёмка и полный текст рисков
из полных карточек в инструмент не выносятся.

**Экран «Почему FINAL» (участник 3).** `app/config/why_final.json` —
формулировки записки (`status`, `headline`, `pareto`, `price`, `robustness`,
`comparator`); альтернативы и их подписи — `config/alternatives.json`; балл,
место и разложение по критериям считает движок. На расчёт файл не влияет.

**Карточка решения (роли C, D, E).** `config/team.json` — название команды,
метод (`Weighted MCDA`), тезис стратегии и шесть управленческих полей из
notebook организаторов (`payer_opex`, `operator_model`, `supplier_switch_rule`,
`replicable_core`, `local_adaptation`, `stress_decision`; кто какое заполняет —
в комментарии файла). Портфель и веса подставляются из `config/portfolio.json`
и `config/weights.json`. Экспорт (CLI и интерфейс) собирает из этого
`results/team_decision_config.json`; на расчёт файл не влияет. Тексты те же,
что в записке, по одному-два предложения.

**Пользовательский режим D.** Читается движком из `config/custom_mode.json`
(пример: `config/custom_mode.example.json`). Перебор и предложения работают
по каноническим режимам A/B/C; режим D участвует только в портфеле,
заданном явно, и помечается в `modes` полем `custom: true`.

**Ширина экрана.** Макет рассчитан на 1280 пикселей и шире; ниже работают три
контрольные точки в `app/static/styles.css`. До 1080 боковая панель всегда
свёрнута в узкий рельс (переключатель «свернуть» при этом скрыт), плитки идут
по две в ряд. До 720 шапка переносится по строкам, вкладки страницы
прокручиваются, плитки и карточки сервисов идут в один столбец. До 520
уменьшаются отступы. Любая таблица лежит в контейнере `.tw` и прокручивается
внутри карточки, а не растягивает страницу; широкие таблицы (`.tw.wide`:
комбинации, лоты, альтернативы, разложение балла, сравнение, матрица запасов)
сохраняют вёрстку и прокручиваются целиком, чтобы столбец состава не
превращался в колонку чипов. Проверено на 1440, 1024, 768 и 400 пикселях:
горизонтальной прокрутки страницы нет ни на одной из пятнадцати вкладок.
Снимки в `app/screenshots/` снимаются на 1600 пикселях и адаптив не
показывают.

## Снимки экранов

`node app/screenshot.mjs` поднимает сервер на 8766 и кладёт в `app/screenshots/`
снимок каждой вкладки каждой страницы: `<страница>.png` — первая вкладка
(светлая тема), `<страница>-<вкладка>.png` — остальные вкладки,
`<страница>-dark.png` — первая вкладка в тёмной теме, `scenario-menu.png` —
открытый выбор сценария, `portfolio-builder-fail.png` и
`portfolio-checks-fail.png` — произвольный портфель с нарушением STRESS
(конструктор и таблица проверок), `portfolio-lots-open.png` — развёрнутая
таблица «Лоты портфеля» (на экране она по умолчанию свёрнута до строки
«лот · режим · c0» и итога). Нужен playwright с Chromium; без доступа
к Google Fonts задать `FONT_DIR`, см. `docs/mockup/README.md`. Снимки в
репозитории сняты с `FONT_DIR` (кэш woff2 Montserrat): headless Chromium в
песочнице до Google Fonts не достаёт и без кэша подставляет системный шрифт.
