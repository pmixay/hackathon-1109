# Космо-портфель: расчётный инструмент Кейса 02

Интерфейс по утверждённому макету (`docs/mockup/`) поверх расчётного движка
команды `src/kosmo`. Без зависимостей, без ключей, офлайн. Свои формулы в
`app/` не хранятся: каждая цифра на экране получена вызовом движка.

## Запуск

```
python app/server.py            # http://127.0.0.1:8765
```

Без сервера: `python app/build.py` собирает `app/static/data/dashboard.json`,
после чего папку `app/static` можно открыть любым статическим сервером
(`python -m http.server -d app/static`). В этом режиме выбор комбинации
работает внутри уже собранного файла, а экспорт недоступен.

Проверки интерфейсного слоя (сверка с движком и с `results/`):

```
python -m unittest discover -s app/tests -v
```

Они же попадают в общий прогон `python -m pytest -q` из корня репозитория.

## Как это устроено

```
app/
├── server.py            сервер: статика + GET /api/dashboard + POST /api/export + /api/data
├── build.py             собрать dashboard.json; --export пишет results/ движком
├── config/
│   ├── model.json       параметры интерфейса: feasible_scenario, thin_margin_pct,
│   │                    allowed_modes, число предложений
│   ├── lots_ui.csv      карточки сервисов: название для интерфейса, описание,
│   │                    пользователь, доступ, KPI, что показать при сбое     ← карточки сервисов (записка)
│   └── lots_ru.json     регионы, архетипы и названия лотов без карточки (только подписи)
config/team.json         карточка решения: команда, метод, тезис, шесть управленческих полей ← роли C, D, E
├── backend/
│   ├── evaluate.py      обёртка над kosmo: load_case, calculate_all_scenarios, строки проверок
│   ├── model.py         перебор через движок, балл (kosmo.score_variants), предложения, действия в стрессе
│   ├── payload.py       сборка dashboard.json, экспорт results/ через kosmo.export_bundle
│   └── ingest.py        загрузка набора данных в формате организаторов (вкладка «Данные»)
├── static/              интерфейс: index.html, styles.css, app.js, data.js, data/dashboard.json
├── tests/               unittest: сверка с движком и results/, форма контракта, экспорт
└── CONTRACT.md          схема dashboard.json
```

Поток данных: `data/`, `config/case_config.json` (копия файлов организаторов,
сверенная движком по `config/case_checksums.json`) → `kosmo.load_case` →
`kosmo.calculate_all_scenarios` для каждой из 5 670 комбинаций →
`kosmo.score_variants` с весами из `config/weights.json` → `backend.payload`
→ `dashboard.json` → `app.js`. Интерфейс не считает модель: только
показывает и выводит производные (см. CONTRACT.md).

Единые источники, общие с CLI движка (`python -m kosmo ...`):

| Что | Где | Кто меняет |
|---|---|---|
| выбранный портфель | `config/portfolio.json` | решение гейта |
| альтернативы для `alternatives.csv` | `config/alternatives.json` | экономист |
| веса и критерии балла | `config/weights.json` | модель выбора |
| пользовательский режим D | `config/custom_mode.json` (если есть) | движок подмешивает его сам |
| карточка решения для `team_decision_config.json` | `config/team.json` | C, D, E |
| цифры для записки | `results/` | только выгрузка движком |

`app/config/model.json` держит лишь параметры экрана. Балл в интерфейсе
считается той же функцией `kosmo.score_variants`, что и `results/scores.csv`,
но нормализуется по всем допустимым в STRESS комбинациям перебора
(`feasible_scenario`), поэтому значения балла на экране и в `scores.csv`
(нормализация по семи альтернативам) не совпадают и не должны.

## Что делает интерфейс

- **Шапка.** Сценарий (BASE/STRESS) выбирается из выпадающего списка; цифры
  лимитов в нём не показываются — они в подсказках «?» и на вкладке
  «Ограничения». Рядом переключатель светлой и тёмной темы (выбор
  запоминается в браузере; без выбора берётся тема системы). Внутри каждой
  страницы — вкладки, адрес вида `#портфель/вкладка` (`#portfolio/combos`).
- **Портфель.** «Обзор» — карточки лотов выбранной комбинации с режимом и c0,
  место по баллу, плитки показателей, сводка девяти ограничений.
  «Комбинации» — предложенные комбинации с отличиями от выбранной (клик по
  строке выбирает; сервер пересобирает предложения относительно новой
  выбранной; портфель из `config/portfolio.json` остаётся в списке всегда).
  Ранжируются все комбинации, допустимые в STRESS (143); модель выбора —
  советник, выбор портфеля управленческий. Столбец «S2 ≥ 0,60» — диагностическая
  проверка команды из `config/weights.json` → `gates` (якорные платежи / OPEX
  при нулевой коммерческой выручке), на балл и ранг она не влияет.
  Переключатель «S2 как фильтр» в заголовке таблицы (`?gates=filter`)
  показывает, как изменился бы список, если бы S2 была правилом отбора:
  остаются 18 комбинаций, портфель команды первый, а лидер без S2 уходит в
  серую строку «не проходит S2».
  «Ограничения» — девять проверок с фактом и порогом для сценария из шапки.
  «Лоты и сервисы» — таблица лотов с итогом и карточки сервисов (что
  получает пользователь каждого лота).
- **Сравнение.** «Графики» — ценность/поступления и c0 относительно лимитов;
  «Таблица» — комбинации с баллом.
- **Стресс.** «Запасы» — матрица запасов по каждому ограничению; «Действия» —
  что можно сделать для комбинации, не проходящей STRESS, и карточка «Замена».
- **Данные.** «Текущий набор» (хэши, версия), «Загрузка» (три файла
  организаторов, проверка, предпросмотр, применение), «Формат».
- Кнопка «Экспорт results/» вызывает `kosmo.export_bundle`: для портфеля
  команды пишет в `results/` те же файлы, что `python -m kosmo export`
  (`base.json`, `stress.json`, `alternatives.csv`, `scores.csv`,
  `sensitivity.csv`, `repairs_base.csv`, `repairs_stress.csv`, а также
  `portfolio_detail.csv`, `portfolio_metrics.json`, `team_decision_config.json`
  с теми же именами и полями, что у последней ячейки стартового notebook
  организаторов, README организаторов §8.8); для любой другой комбинации —
  в `results/variants/<id>/`, чтобы цифры записки не затирались случайным
  кликом.
- Пояснения не лежат на экране серым текстом: у каждого блока кнопка «?»,
  по клику открывается подсказка для эксперта (пороги, формулы, правила
  кейса, единицы измерения).

## Что где менять

**Движок (`src/kosmo`).** Формулы, проверки, заметки, перебор, выгрузка.
Интерфейс их не дублирует; тесты `app/tests` падают, если dashboard
разошёлся с `results/base.json` или с прямым вызовом движка.

**Модель выбора.** `config/weights.json` — критерии, направления, веса,
обоснования (ключ `margin:STRESS:c0_limit` показывается как «запас по
STRESS»). `model.suggest` — правило отбора предложений (лучший режим
каждого допустимого набора лотов + режим A на всех лотах выбранного
набора, топ-N по баллу, плюс отвергнутая с максимумом ценности).
Чувствительность к весам ±20 % уже есть в `results/sensitivity.csv`.

**Стресс.** `model.stress_actions` формирует список «что можно сделать»
для комбинации `stress.failing`; правило кейса (стоимость лотов не
снижается) соблюдено: только смена режима или состава. Подписи действий —
из `describe_change`. Полный список одношаговых замен для портфеля команды —
`results/repairs_stress.csv`.

**Гейт.** Выбранный портфель — `config/portfolio.json` в формате движка
(`name`, `selection` из пар `lot_id`/`mode_id`, `note`). Порядок лотов
не важен: интерфейс приводит id к порядку `lots.csv`.

**Карточки сервисов (записка).** `config/lots_ui.csv` — файл в формате
«участник 5», который готовит автор карточек сервисов: `lot_id`, «Название для интерфейса», «Короткое
описание», «Основной пользователь», «Режим», «Базовый доступ»,
«Дополнительный доступ», «Главный KPI», «Что показать при сбое». Название
лота в интерфейсе берётся отсюда, поэтому в записке и на экране оно одно;
остальные поля идут в блок «Сервисы портфеля». Строки можно добавлять для
любых лотов; лот без строки показывается по `lots_ru.json` с пометкой
«карточка не подготовлена». Плательщик, оператор, приёмка и риски из полных
карточек в инструмент не выносятся.

**Карточка решения (роли C, D, E).** `config/team.json` — название команды,
метод (`Weighted MCDA`), тезис стратегии и шесть управленческих полей из
notebook организаторов (`payer_opex`, `operator_model`, `supplier_switch_rule`,
`replicable_core`, `local_adaptation`, `stress_decision`; кто какое заполняет —
в комментарии файла). Портфель и веса подставляются из `config/portfolio.json`
и `config/weights.json`. Экспорт (CLI и интерфейс) собирает из этого
`results/team_decision_config.json`; на расчёт файл не влияет. Тексты те же,
что в записке, по одному-два предложения.

**Пользовательский режим D.** Читается движком из `config/custom_mode.json`
(пример: `config/custom_mode.example.json`). Перебор и предложения работают
по каноническим режимам A/B/C; режим D участвует только в портфеле,
заданном явно, и помечается в `modes` полем `custom: true`.
