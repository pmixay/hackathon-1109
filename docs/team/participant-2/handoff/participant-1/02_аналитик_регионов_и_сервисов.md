# Участник 2 — аналитик регионов и организации сервисов

## Твоя цель

Закрыть главный «человеческий» слой проекта:

> кому нужен каждый сервис, кто за него платит, какое решение принимает пользователь, как устроен доступ, какие есть риски и что переносится между регионами.

Твоя зона напрямую поддерживает П1, П5, П7 и П8.

Финальный портфель:
`FIRE-A + ENV-A + AGRI-B + TRANS-B`.

---

## Приоритет 1. Финальные карточки четырёх сервисов

Для каждого сервиса должна быть короткая цепочка:

`проблема → пользователь → сервис → действие пользователя → результат → KPI → источник проверки`

### FIRE-A
Нужно зафиксировать:
- проблема: позднее обнаружение потенциальных очагов на большой территории;
- пользователи: лесные/диспетчерские службы, службы ЧС;
- действие: проверить сигнал и расставить приоритет реагирования;
- эффект: более раннее управленческое решение;
- не обещать автоматически «сокращение площади пожара» без подтверждения;
- предполагаемый плательщик: МЧС — только как гипотеза по консультации, полномочия по лесной части требуют уточнения.

### ENV-A
- пользователи: природоохранные органы, муниципалитеты;
- действие: выбрать зону риска и назначить наземную проверку;
- эффект: адресный контроль и сопоставимая история наблюдений;
- предполагаемый плательщик: Минприроды — гипотеза, не установленный факт.

### AGRI-B
- пользователи: хозяйства, агрономы, органы АПК;
- действие: выбрать поле/участок для обследования или обработки;
- эффект: более обоснованное использование ресурсов;
- якорный плательщик: Минсельхоз — гипотеза команды;
- коммерческие пользователи: хозяйства, кооперативы, страховщики.

### TRANS-B
- пользователи: транспортные органы, инфраструктурные операторы, перевозчики;
- действие: приоритизировать обследование/эксплуатационное решение;
- эффект: более раннее выявление отклонений;
- Росавтодор — только для дорожной части и только как предполагаемый плательщик.

## Приоритет 2. Содержательно объяснить режимы A и B

Организаторы дали коэффициенты режимов, но не готовое юридическое содержание. Поэтому содержательная интерпретация — ваше проектное решение.

### A для FIRE и ENV
Защищаемая логика:
- общественно значимый базовый слой;
- доступ уполномоченным органам по публичному контракту;
- базовый результат гарантируется;
- история, интеграции и расширенная аналитика могут идти отдельным договором;
- `public_core = true`.

Не говорить:
> «режим A означает всё бесплатно и открыто всем в интернете».

### B для AGRI и TRANS
Логика:
- якорный заказчик получает агрегированный слой;
- подключённые организации получают данные своих территорий/объектов;
- детальная аналитика, история, API и интеграции могут быть платными;
- B нельзя называть полностью коммерческим, потому что якорная компонента сохраняется.

## Приоритет 3. Карта участников

Оформить понятную схему:

**Межрегиональный заказчик**
- задаёт цели;
- утверждает каталог сервисов;
- устанавливает требования и правила доступа.

**Единый оператор**
- управляет доступом;
- SLA;
- интеграциями;
- поддержкой;
- журналами;
- сквозным качеством.

**Поставщики данных/аналитики**
- поставляют компоненты по открытым требованиям.

**Региональная принимающая сторона**
- проверяет применимость результата;
- подтверждает KPI;
- встраивает сервис в процесс.

**Пользователь**
- получает сигнал;
- проверяет;
- принимает решение;
- фиксирует результат.

Передать эту схему участнику 1 для записки и слайда.

## Приоритет 4. Реестр рисков

Финальный реестр должен быть привязан именно к вашему портфелю.

Обязательные строки:

1. Задержка/пробел исходных данных.
2. Ложный или пропущенный сигнал.
3. Зависимость от одного поставщика.
4. Сервис не встроен в рабочий процесс региона.
5. Неправомерный доступ/раскрытие данных.
6. Коммерческий спрос ниже модели.
7. Ошибка причинности KPI: эффект приписали сервису без доказательства.
8. Задержка бюджетных платежей и закупочных процедур.

Для каждой строки:
- событие;
- причина;
- последствие;
- ранний сигнал;
- мера;
- владелец;
- остаточный риск;
- ограничение меры.

Особенно не потерять риск задержки бюджетных платежей — это замечание с консультации трекера.

---

## Приоритет 5. Смена поставщика и конкуренция

Зафиксировать правило:

Смена поставщика запускается при:
- повторном нарушении критического SLA;
- двух последовательных провалах качества;
- утрате права на данные;
- отказе от открытого экспорта;
- необоснованном превышении договорного ценового предела.

Должны передаваться:
- история;
- настройки;
- API-спецификации;
- журналы качества;
- инструкции.

Новый поставщик:
- проходит контрольный пересчёт на эталонном наборе;
- работает параллельно в переходный период.

В договорной модели предусмотреть:
- права заказчика на историю и результаты;
- CSV/GeoJSON или другой машиночитаемый открытый экспорт;
- документированное API;
- возможность нескольких поставщиков;
- порядок оплаты перехода.

## Приоритет 6. Тиражирование

### Что переносится готовым
- каталог сервисов и ролей;
- конвейер обработки;
- модель событий;
- API и форматы;
- доступ и журналирование;
- шаблоны SLA;
- методика KPI;
- договорные шаблоны;
- база знаний оператора.

### Что адаптируется локально
FIRE:
- границы;
- сезонные пороги;
- каналы диспетчеризации.

ENV:
- контролируемые зоны;
- типы событий;
- правила инспекций.

AGRI:
- границы полей;
- культуры;
- сезоны;
- права хозяйств.

TRANS:
- перечень объектов;
- маршруты;
- интеграции;
- регламенты реакции.

### Как передаётся опыт
После каждого пилота:
1. собрать ошибки/задержки/изменения;
2. обновить типовое ядро;
3. обновить KPI и договорные шаблоны;
4. сохранить новую версию базы знаний;
5. новый регион стартует уже с обновлённой версии.

## Приоритет 7. Поля `team.json`

Проверить вместе с участником 1:

Твоя зона:
- `operator_model`
- `supplier_switch_rule`
- `replicable_core`
- `local_adaptation`

Если первые два уже заполнены — вычитать на соответствие финальной записке, а не переписывать без причины.

## Что НЕ делать

- Не называть ведомства подтверждёнными заказчиками.
- Не говорить, что SLA уже реализованы программно.
- Не говорить, что спутниковый сигнал сам «тушит пожар» или «предотвращает аварию».
- Не смешивать `vpub` и денежные потоки.
- Не обещать причинный эффект без наземной проверки.
- Не придумывать новые числа вместо исходных данных организаторов.
