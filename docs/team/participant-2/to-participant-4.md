# Передача участнику №4: данные, события и контроль качества

Для технической схемы нужны единые поля события:

| Поле | Зачем |
|---|---|
| `event_id`, `lot_id`, `territory_id` | Однозначно связать сигнал с сервисом и территорией |
| `observed_at`, `published_at`, `source_updated_at` | Измерять свежесть и задержку |
| `geometry` или `object_id` | Показать зону, маршрут, поле или объект |
| `source_type`, `provider_id`, `processing_version` | Обеспечить аудит и смену поставщика |
| `confidence`, `quality_flags` | Не выдавать неопределённый сигнал за подтверждённый факт |
| `status` | `new → acknowledged → field_check → confirmed/rejected → closed` |
| `assigned_org`, `assigned_user` | Понять, кто должен отреагировать |
| `decision_at`, `decision_type` | Измерить действие пользователя, а не только выпуск карты |
| `accepted_by`, `accepted_at` | Зафиксировать приёмку результата |
| `access_class` | Разделить базовый, служебный и дополнительный слой |

Технически нужно подтвердить: допустимые источники по каждому лоту, частоту обновления, работу при облачности и пробелах, резервный канал, экспорт истории, открытый API, журнал доступа и контрольный набор для нового поставщика.

Самое полезное для участника №4 — поля `source_updated_at`, `provider_id`, `processing_version`, `confidence`, `status` и `decision_at`: без них нельзя доказать SLA, пользу или переносимость.
